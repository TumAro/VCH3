# Manager Assistant and Evidence-Retrieval Chat
- Status: Implemented
- Created: 2026-11-21

## 1. Spec

### Goal and context

Add a chat-style Manager Assistant to the existing dashboard. The assistant will answer trend and summary questions and produce a short, actionable daily task list for area managers and merchandisers.

The feature will use retrieval over verified application data and project rules before calling a configurable Sarvam AI-compatible language endpoint. The language model may summarize and formulate actions, but it may not calculate facts or invent unavailable evidence.

### Scope

**In scope:**
- A chat panel in the existing dashboard.
- Daily manager briefing with at most five tasks ranked by rupee impact or stock impact.
- Trend summaries for monthly state and city revenue, network stock, findings, moves, and notifications.
- Store or area-manager scoped questions.
- Evidence citations for each numerical claim or recommendation.
- Configurable API-key authentication for Sarvam AI.
- A fallback response when the assistant is offline or an API key is missing.
- A repository-backed evidence retrieval layer for application facts and documented business rules.

**Out of scope:**
- Direct stock recommendations calculated by the language model.
- Writing or approving ERP/WMS changes.
- Replacing deterministic move generation or constraint validation.
- External web search.
- Multi-user authentication or chat history synchronization.
- Store Coach conversion, staffing, basket, or repeat-customer coaching until the corresponding footfall, roster, salesperson, and customer data is ingested and tested.
- Automatic phone calls, emails, WhatsApp messages, or other push actions.

### Requirements

- **REQ-1:** The assistant must answer from application state and retrieved project evidence; it must not guess or hallucinate source values.
- **REQ-2:** The assistant must support natural-language requests for a network summary, state or city trends, store trends, stock findings, move summaries, and daily tasks.
- **REQ-3:** Each numerical fact in an answer must be linked to a visible source reference containing the metric name, scope, value, and source table or result type.
- **REQ-4:** The daily briefing must contain no more than five tasks and must rank them by rupee impact or stock impact.
- **REQ-5:** Every daily task must name the owner or store, the action, the expected impact or reason, and the timing or deadline that can be derived from existing data.
- **REQ-6:** The system must support Sarvam AI through a server-side API-key configuration and must not expose, log, or persist the API key in browser storage or source code.
- **REQ-7:** If evidence is unavailable or insufficient, the assistant must say that no reliable conclusion is available and must identify the missing data instead of filling the gap.
- **REQ-8:** The chat endpoint must fail safely when the provider is unreachable, the key is missing, or provider output is malformed.
- **REQ-9:** Existing dashboard behavior must remain available if the assistant provider is unavailable.
- **REQ-10:** Chat responses must be deterministic in evidence selection for a given application state and query, with provider-specific wording allowed to vary.
- **REQ-11:** All factual calculations used by the assistant must be owned by existing or new typed services, not embedded in prompt text or generated by the model.
- **REQ-12:** The assistant UI must clearly label generated language separately from verified facts and must prevent untrusted model text from being interpreted as HTML or executable content.
- **REQ-13:** The feature must exclude packaging SKUs and untrusted quarantined stock rows from every inventory fact.
- **REQ-14:** Provider configuration and retrieval settings must be environment/config driven, with the key supplied outside version-controlled source.

### Acceptance criteria

- **AC-1 (REQ-1, REQ-3):** In a fixed test dataset, every answer with a numeric claim cites at least one matching source reference and no answer invents a source value.
- **AC-2 (REQ-2):** The assistant returns useful summaries for network, state, city, store, findings, moves, and notifications query categories.
- **AC-3 (REQ-4, REQ-5):** The generated daily briefing contains one to five tasks, ranked highest first, with owner/store, action, reason or impact, and timing or no unsupported timing claim.
- **AC-4 (REQ-6, REQ-14):** A configured key reaches the provider only from the server, and missing or empty configuration prevents provider calls without crashing the dashboard.
- **AC-5 (REQ-7):** A store with no usable evidence produces an insufficient-evidence response instead of a speculative trend or recommendation.
- **AC-6 (REQ-8, REQ-9):** Provider timeout or malformed output returns a visible fallback, and overview, moves, notifications, re-run, and exports continue working.
- **AC-7 (REQ-10, REQ-11):** Two requests against the same evidence set retrieve the same facts and rankings; only prose wording may differ.
- **AC-8 (REQ-12):** Model output containing HTML or script-like text is rendered as plain text.
- **AC-9 (REQ-13):** Packaging SKUs and quarantined stock never appear in cited inventory evidence or daily tasks.
- **AC-10:** The feature adds a usable chat panel and one-click daily briefing to the existing dashboard without reloading the page.

### Edge cases and failure modes

- **No API key:** The app shows the chat panel disabled or in a factual-only mode and explains that provider setup is required.
- **Provider timeout:** The app returns no fabricated answer and offers the last verified briefing or summary when available.
- **No recent evidence:** The app reports that the current evidence set is too old or incomplete.
- **Ambiguous scope:** A query such as "How is Bengaluru?" must ask for or present a store/city/state scope if one cannot be inferred safely.
- **Contradictory evidence:** Retrieved data issues take precedence for affected values; the answer labels them untrusted rather than blending them into a valid total.
- **Seasonal or regional swings:** Revenue dips and rises must not be presented as failures without matching seasonal context from the existing calendar and peer comparison.
- **Missing Store Coach sources:** Conversion, basket, repeat, and staffing questions must identify the missing source tables or say that the MVP cannot judge them.

### Assumptions and open questions

- The initial MVP uses Sarvam AI as a provider behind an OpenAI-compatible or provider-specific adapter selected through configuration.
- The API key will be supplied later and is not available during spec planning.
- "RAG" means retrieval over structured application results and versioned project documentation, not a mandatory vector database for the MVP.
- The initial evidence store may use deterministic in-memory or file-backed retrieval; a vector database is deferred unless data or query quality demonstrates it is necessary.
- The implementation must preserve the existing repository pattern and must not query CSV files directly from the assistant service.
- Pending approval at this gate is the exact feature scope; provider endpoint details and credentials will be handled as configuration assumptions, not guessed in the spec.

### 2.3 Evidence and data contracts

- Evidence records are immutable and contain a stable source ID, source type, scope, metric name, value, unit, supporting key fields, and source table or result model.
- Source types include network overview, monthly revenue, store revenue, stock position, finding, move, data issue, notification, and approved project rule.
- The evidence service will use existing repository and service results rather than raw CSV access.
- Citations will refer to stable source IDs and human-readable labels. Numerical answers will include the exact value returned by the evidence record.
- The provider receives only a selected evidence bundle and the user's question. It does not receive credentials, raw CSV files, or unrestricted repository access.
- The provider response is schema-validated or rejected. It may paraphrase evidence but may not add numbers, owners, stores, deadlines, or actions absent from the evidence bundle or approved task templates.
- Daily tasks use a fixed task template: owner/store, action, reason, timing, impact value, rank, and evidence IDs.

### 2.4 Retrieval strategy

- MVP retrieval will be lexical and structured: classify the query into network, state, city, store, moves, findings, notifications, or daily briefing; narrow evidence by store/city/state; then rank evidence by scope match and rupee or stock impact.
- Project documentation may be indexed as short versioned chunks at startup or from a checked-in corpus. No unreviewed free-text answer may be treated as factual evidence.
- Vector embeddings are deferred. They add provider or dependency cost without a demonstrated need for the 17-table MVP.

### 2.5 Dependencies

- Use the existing Python standard library and FastAPI stack.
- Use the existing `httpx` test/runtime dependency if already available in the environment to call Sarvam AI.
- Use no new vector database or embedding package in the MVP.
- Any provider SDK is added only after the provider contract is known from the user's API-key setup. Prefer the provider HTTP API or an existing compatible endpoint.

### 2.6 Risks and trade-offs

- **Hallucinated numbers:** Mitigated by a typed evidence bundle, strict response validation, and server-owned calculations.
- **Model action overreach:** Mitigated by approved task templates and no tool execution by the language model.
- **Provider lock-in:** Mitigated by an interface and adapter, with provider-specific code isolated to one module.
- **Unsupported Store Coach claims:** Mitigated by explicitly unavailable-data responses until footfall, roster, salespeople, customer repeat, and calendar ingestion are implemented.
- **Stale evidence:** Mitigated by snapshotting evidence in `DataContext` and refreshing it after successful re-run.
- **Key leakage:** Mitigated by environment-only credentials, server-only use, and tests that reject browser/config file keys.
